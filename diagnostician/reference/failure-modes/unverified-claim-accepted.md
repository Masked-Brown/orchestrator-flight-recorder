# Unverified claim accepted

**In one line.** A confident explanation was taken at face value when checking it would have been
cheap, and everything after it was built on something untrue.

## What it is

Someone asserted how a thing works, what a file contains, what happened, or why. It was stated
with the flatness of established fact. Nobody checked. It was wrong.

Confidence did the work that evidence should have done. That is the mechanism, and it is worth
being precise that **the mode is the acceptance, not the claim.** Wrong claims are cheap and
constant; what makes this a failure is that a check was available, affordable, and did not
happen.

Either party can make the claim and either can accept it. A model asserting something about a
file it has not opened, and a person asserting something about a tool's behaviour from memory,
are the same mode.

Three things must all be present:

1. **A specific assertion** — not a hedge, not an impression. Something that could be true or
   false.
2. **A cheap check that was available** at that moment.
3. **The check not happening** before the work continued.

## What it looks like in the record

- **A definite statement with no supporting action anywhere near it.** A claim about file
  contents, tool behaviour, what a previous step produced, or why something happened — and no
  tool call before or after it that would have established any of that.
- **The next turns proceeding as though it were settled.** No question, no verification, no
  hedging carried forward.
- **A later contradiction on the record** — a tool result, a correction, a discovery that shows
  the claim was false. Without this you have an unchecked claim, not a failed one.
- **Visible cheapness.** The same session shows the very tool that would have settled it being
  used routinely, before or after. This is what turns "they should have checked" into an anchored
  claim, and you need it: quote the message where that tool is used elsewhere.
- **In the reasoning channel, where you have it:** an assertion appearing with no weighing at all
  of whether it is actually known — which distinguishes a guess presented as fact from a
  considered position that happened to be wrong.

## Telling it apart

| Easily confused with | The question that separates them |
|---|---|
| `missing-context` | Would supplying a **fact** have prevented it, or would **checking an assertion** have prevented it? Fact → missing context. Check → this. |
| `vocabulary-mismatch` | Could the claim have been checked **as written**? If the register made it uncheckable, the failure is the register. |
| `premature-parallelism` | Was the thing taken on trust a **statement** or a **piece of work**? Statement → this. Work built on unverified work → parallelism. |
| `ambiguous-instruction` | Was something **misread**, or was something **asserted and believed**? |

## What rules it out

- **The check happened.** If the record shows verification and the thing was still wrong, look at
  the verification instead — that is a different failure with a different origin.
- **No cheap check existed.** If confirming it would have required something not available inside
  the session, accepting it was a reasonable act and this is not the mode. The cheapness is part
  of the claim and has to be shown, not assumed.
- **The claim was true.** A confident assertion that happens to be correct causes nothing,
  however unsupported it was at the time.

## A note on the verdict

This mode is deliberately silent about whose fault it was, and the verdict does real work here.
The same mechanism can land in three different places:

- The model asserted something false and the instruction was determinate → `mechanical`. This is
  the acquittal case: the person had no reason to doubt it and the record shows why.
- The person asserted something false from memory and the model built on it → `pilot-error`.
- Both had the means to check and neither did → `mixed`, with the earlier one named primary.

Decide it from the record, not from who is reading the report.
